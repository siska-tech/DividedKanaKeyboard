# 分割型かなキーボード（薙刀式）要件定義書

**プロジェクト名:** DividedKanaKeyboard（Naginata Split Keyboard）
**版数:** 0.3（ドラフト）
**作成日:** 2026-06-09
**確定事項:** 出力方式=ローマ字シーケンス／BLE給電=モバイルバッテリ(PoC)／ファーム基盤=Rust(embassy)優先・不可ならC/C++(pico-sdk)／役割=USB列挙でマスタ自動化・手番=EE_HANDS（左右同一FW）／配列定義=build.rs codegen(YAML→phf)／判定窓=既定40ms／ピンアサイン確定（§2.1）

## 1. 目的・背景

左右2分割の自作キーボードを、各半身に搭載した **Raspberry Pi Pico W** で制御し、
両機を **シリアル通信（UART）で連携** させながら、ホストPCに対して **USB / Bluetooth(BLE) の HIDキーボード** として動作させる。

入力方式として **薙刀式 v15（fix版）** の「同時打鍵によるかな入力」をファームウェア側で実装し、
ホスト側に専用の入力支援ソフト（やまぶき・DvorakJ 等）を導入しなくても薙刀式が利用できることを目指す。

> 薙刀式は「重要な言葉の運指が容易」を狙ったローマ字配列・カタナ式系統の同時打鍵かな配列。
> 単打・センターシフト・連続シフト・後置シフト・2〜3キー同時押し・濁音/半濁音/拗音/外来音/編集モードを持つ。

## 2. システム構成（ハードウェア）

添付 BOM / 回路図（SCH_Naginata-left / -right）に基づく。

| 区分            | 部品                                 | 数量（片側） | 備考                                                         |
| --------------- | ------------------------------------ | ------------ | ------------------------------------------------------------ |
| MCU             | Raspberry Pi Pico W (U1)             | 1            | USB / 無線(BLE)対応。左右で各1基、計2基                      |
| キースイッチ    | Cherry MX1A-11NW                     | 35           | 片側35キー、左右合計70キー                                   |
| ダイオード      | M7（汎用整流, SMA）                  | 35           | キーごとに1個。**フルNKRO（Nキーロールオーバ）を成立させる** |
| インジケータLED | WS2812B-2020                         | 1〜2         | シリアルRGB（アドレサブル）                                  |
| 連結コネクタ    | PJ-320DB-5A（4極ジャック, TRRS相当） | 1            | 左右間配線: **+5V / GND / TX / RX**                          |
| 配線（Pico）    | GP0=UART0 TX, GP1=UART0 RX           | –            | 左右連結用シリアル                                           |
| マトリクス      | col×row（ダイオードマトリクス）      | –            | row/col を Pico GPIO に割当てスキャン                        |

**ハードウェア上の重要事項**
- キーごとにダイオードが入っているため **同時押しの取りこぼしが原理的に発生しない（フルNKRO）**。薙刀式の同時打鍵検出に必須の前提を満たす。
- 左右連結は **有線UART（TRRSケーブル）**。+5V/GND を含むため、マスタ側USB給電をスレーブ側へ供給可能。
- Pico W のため、ホストとの接続は **USB（有線）／BLE（無線）** の両対応が可能。

### 2.1 ピンアサイン（確定 / 左右共通・回路図準拠）

マトリクスは **14列 × 6行（col0–13 × row0–5）= 84交点中35キーを使用**（疎マトリクス）。

| 物理pin | RP2040 | 用途         | 物理pin | RP2040 | 用途          |
| ------- | ------ | ------------ | ------- | ------ | ------------- |
| 1       | GP0    | UART0 **TX** | 21      | GP16   | row0          |
| 2       | GP1    | UART0 **RX** | 22      | GP17   | row1          |
| 4       | GP2    | col0         | 24      | GP18   | row2          |
| 5       | GP3    | col1         | 25      | GP19   | row3          |
| 6       | GP4    | col2         | 26      | GP20   | row4          |
| 7       | GP5    | col3         | 27      | GP21   | row5          |
| 9       | GP6    | col4         | 29      | GP22   | NC（予備）    |
| 10      | GP7    | col5         | 31      | GP26   | NC（予備）    |
| 11      | GP8    | col6         | 32      | GP27   | NC（予備）    |
| 12      | GP9    | col7         | 34      | GP28   | WS2812B DIN   |
| 14      | GP10   | col8         | 40      | VBUS   | +5V（TRRSへ） |
| 15      | GP11   | col9         | –       | –      | –             |
| 16      | GP12   | col10        |         |        |               |
| 17      | GP13   | col11        |         |        |               |
| 19      | GP14   | col12        |         |        |               |
| 20      | GP15   | col13        |         |        |               |

- **TX/RX はTRRSコネクタ側で左右クロス配線**（一方のTX→他方のRX）。よって**左右で全く同一のファーム／配線**でよい（ストレート結線として扱える）。
- 予備 **GP22 / GP26 / GP27** は未使用。将来の手番（handedness）ストラップ等に転用可能。
- スキャン方式: 列(14)より行(6)が少ないため **行(row0–5)をストローブし列(col0–13)を読む** 構成が高速（6ステップ）。ただし実際の駆動方向はダイオード極性に依存するため、ブリングアップ時に極性（ROW2COL / COL2ROW）を実測で確定する。

## 3. 全体アーキテクチャ

### 3.1 マスタ／スレーブ構成【左右同一ファーム・自動判定】
- **マスタ（主）**: ホスト（PC）と USB もしくは BLE で接続。HID出力を担う。
- **スレーブ（従）**: 自半身のマトリクスをスキャンし、キー状態（押下/解放イベント）を **UART で随時マスタへ送信**。
- マスタは「自半身のキー状態」＋「スレーブから受信したキー状態」を統合し、**薙刀式変換エンジン**へ渡す。

**役割の自動判定（USB側を自動マスタ化）**
- **判定方法はVBUSの有無ではなく「USBエンタメレーション（ホストとの接続確立）の成否」で行う。**
  理由: TRRSの+5Vが両半身のVBUSに供給されるため、スレーブ側VBUSも5Vになり得る。電源有無では判別できない。
- 起動後、一定時間内に **USBホストとして列挙される（SOF受信／Configured状態）** 側を **マスタ**、列挙されない側を **スレーブ**（UART従動）とする。動的な抜き差しにも追従する。

**手番（左右）の判定 — EE_HANDS方式**
- 薙刀式は左右で論理キー割当が異なるため、各半身は自分が左か右かを知る必要がある。
- **同一バイナリのまま**、各Picoのフラッシュ末尾セクタに手番（`L`/`R`）を1バイト保存する **EE_HANDS方式** を採用（QMK同手法）。
- 書込みは初回プロビジョニング時に一度だけ実施（専用書込みツール、または特定キー押下起動での設定）。以降は同一FWで左右を区別。
- マスタは「自分の手番の配列表」を自分のマトリクスへ、「反対側の配列表」をスレーブ受信分へ適用する。

```
[左 Pico W]──UART(TRRS)──[右 Pico W]──USB/BLE──[ホストPC]
   scan                     scan + 統合 + 薙刀式変換 + HID出力
 (スレーブ例)                    (マスタ例)
```

### 3.2 接続モード
| モード    | ホスト接続       | 左右連結 | 給電                                     |
| --------- | ---------------- | -------- | ---------------------------------------- |
| USBモード | マスタが USB-HID | 有線UART | マスタUSB→スレーブへ+5V供給              |
| BLEモード | マスタが BLE-HID | 有線UART | **モバイルバッテリ（USB給電）** ※PoC方針 |

> **電源方針（確定 / PoC）:** BLE運用時はマスタ側 USBポートに **モバイルバッテリ** を接続して給電する（マスタ→TRRSの+5V→スレーブへ供給）。
> 現BOMに電池・充電回路は無いため、内蔵バッテリによる完全無線化は本PoCのスコープ外（将来課題）。

## 4. 機能要件

### FR-1 キーマトリクススキャン
- FR-1.1 各 Pico は自半身のダイオードマトリクスを周期スキャンし、各キーの押下/解放を検出する。
- FR-1.2 スキャン周期は同時打鍵判定に十分な分解能（**1スキャン ≦ 1〜2 ms**）とする。
- FR-1.3 チャタリング除去（デバウンス）を行う。デバウンス時間は同時打鍵判定を阻害しない範囲（例 5ms前後、調整可能）とする。
- FR-1.4 フルNKRO（35キー同時を含む任意同時押し）を取りこぼさない。

### FR-2 左右間シリアル通信
- FR-2.1 スレーブはキーイベント（キー番号＋押下/解放＋タイムスタンプ）をマスタへUART送信する。
- FR-2.2 通信は低レイテンシ（片道遅延が同時打鍵判定窓に対して十分小さいこと、目安 **≦ 2 ms**）。
- FR-2.3 ボーレートは確実性とレイテンシを両立する値（例 115200bps 以上）を選定。
- FR-2.4 ケーブル抜き差し・ノイズに対する再同期／エラー検出（フレーミング、チェックサム等）を備える。
- FR-2.5 起動時に役割を自動決定する: **USB列挙に成功した側をマスタ**、他方をスレーブとする（§3.1）。手番（左右）はEE_HANDSのフラッシュ値で判定。抜き差しによる役割変化にも追従する。

### FR-3 同時打鍵判定エンジン（薙刀式 v15）
本システムの中核。マスタ上で左右統合後のキー入力列に対し、薙刀式の打鍵規則を適用する。

- FR-3.1 **単打**: 同時押しが成立しないキーは単打定義に従い出力。
- FR-3.2 **同時打鍵判定窓**: 一定時間窓（例 既定 **30〜50 ms**、ユーザ調整可）内に押されたキー群を「同時押し」として扱う。
- FR-3.3 **センターシフト**: スペース（{S}）を伴う同時押しでシフト面を出力。
- FR-3.4 **連続シフト**: シフトキー押下中に続くキーへシフトを継続適用。
- FR-3.5 **後置シフト**: 先行キー＋後続シフトの順序依存の組み合わせを処理（薙刀式の濁音/拗音定義）。
- FR-3.6 **2キー／3キー同時押し**: 濁音・半濁音・拗音・外来音・促音・撥音・記号等の多鍵組合せを定義通りに出力。
- FR-3.7 **逆順許容**: 同時押し系は左右・順序の差を吸収（定義は逆順も成立）。
- FR-3.8 配列定義は薙刀式 v15fix のテキスト定義（添付 `Nagitanashiki_v15fix_version*.txt`）と等価な対応表を内蔵する。
  - メイン配列（単打・センターシフト）
  - 濁音/半濁音/拗音/外来音（前置・後置・二重シフト）
  - 拗音・外来音の3キー同時押し
  - 横書き/英数字版の差分（`*_Horizon` / `*_alphabetnumeric*`）の取り込み可否を選択可能とする。

### FR-4 出力方式（ホストへのHID送信）
- FR-4.1 **【確定】ローマ字シーケンス出力方式を採用する。** 薙刀式の変換結果（かな）を、英字スキャンコード列（例: 「か」→`k`,`a`、「ぎゃ」→`g`,`y`,`a`）として送出し、ホストの **標準ローマ字入力IME** で確定させる。ホスト側に専用ソフトの追加設定を不要とする。
  - 「ん」は後続文字で挙動が変わるため `n`,`n` 送出を基本とする等、ローマ字綴りの曖昧性を解消する変換規則を定義する。
  - 促音「っ」「ー」、記号、数字、英数字版面はローマ字／そのままの文字キーとして送出する。
- FR-4.2 マクロ的出力（編集モードのショートカット、定型文、Enter/BS/カーソル等の制御）を送出できる（添付定義の編集モード1/2・固有名詞ショートカット相当）。
- FR-4.3 IME ON/OFF を制御（薙刀式定義の LANG1/LANG2 = ひらがな/半角・全角 相当キー送出。HJ=ON / FG=OFF 等）。
- FR-4.4 薙刀式（かな入力レイヤ）と、通常のQWERTY/英数・記号レイヤを切替えられる。

### FR-5 USB / Bluetooth 切替
- FR-5.1 マスタは USB-HID と BLE-HID を切替えて動作できる。
- FR-5.2 USB接続検出時はUSB優先、未接続かつ給電ありの場合はBLEへフォールバック等、切替ポリシーを定義する。
- FR-5.3 BLEは複数ホストのペアリング保持・切替（任意）。

### FR-6 LEDインジケータ（WS2812B）
- FR-6.1 状態表示: 接続モード（USB/BLE）、マスタ/スレーブ、現在レイヤ（薙刀/英数）、IME状態、ペアリング等を色/点滅で表示。
- FR-6.2 輝度・色はユーザ設定可能（省電力配慮）。

### FR-7 設定・保守
- FR-7.1 同時打鍵判定窓・デバウンス・出力方式・LED等の主要パラメータを変更可能（再ビルド or ランタイム設定）。
- FR-7.2 ファーム書込みは Pico の BOOTSEL（UF2ドラッグ＆ドロップ）で行える。
- FR-7.3 配列定義データはソースと分離し、メンテナンス可能な形式で保持する。

## 7. 検証・受入要件

- TC-1: 単打・センターシフト・連続シフト・後置シフトの各代表打鍵が定義通り出力される。

## 8. 実装方針（技術スタック）

### 8.1 ファーム基盤【確定: Rust優先、不可ならC/C++】
- **第1候補: Rust（embassy）**
  - フレームワーク: [`embassy`](https://embassy.dev)（async/await ベースの組込みフレームワーク、RP2040対応）。
  - USB-HID: `embassy-usb` の HIDクラスで実装（実績十分）。
  - 無線(BLE): Pico W の CYW43 を `cyw43` ドライバで駆動し、BLEホストスタック（`trouble-host` 等）で BLE-HID を実装。
  - WS2812B: RP2040 の **PIO** を Rust から駆動（`pio` / 既存クレート）。
  - UART(左右連結): `embassy-rp` の UART ドライバ。
  - **リスク:** CYW43 上の Rust製 BLEスタックは比較的新しく成熟度が低い。USB-HIDは問題ないが、BLE-HID が Rust で安定実装できないと判明した場合は下記C/C++へ切替える。
- **フォールバック: C/C++（pico-sdk + TinyUSB + BTstack）**
  - USB-HID: TinyUSB。BLE-HID: pico-sdk 同梱の **BTstack**（Pico W で実績あり）。WS2812B: pico-sdk の PIO 例（ws2812.pio）。
  - 薙刀式の既存実装（QMK `naginata` 等）のロジックを参考・移植可能。
- **判断ポイント:** まず Rust(embassy) で **USB-HID版 PoC** を成立させ、続いて BLE-HID を試行。BLEがRustで詰まったらC/C++へ。エンジン本体（同時打鍵判定・ローマ字変換）は言語非依存に設計し移植容易にする。

### 8.2 確定した設計事項

1. **マスタ/スレーブ決定方式【確定】**: USB列挙の成否で自動マスタ化（§3.1）。手番は EE_HANDS（フラッシュ保存）で左右同一FW。
2. **同時打鍵判定窓【確定（既定値）】**: 既定 **40 ms**（30〜50msの中央）。ランタイム調整可（FR-7.1）。打鍵の「先頭キー押下」から窓を開き、窓内の押下キー集合で組合せ判定。チューニングは実打で最終調整。
3. **配列定義の保持形式【確定】**: **ビルド時コード生成（build.rs）方式**。MCU上ではパースしない。
   - 著作（編集）フォーマット: **YAML で問題なし**（後述）。著作データは `build.rs`（ホスト側=std利用可）で読み、Rustの **静的const表 + コンパイル時パーフェクトハッシュ（`phf` crate）** へ変換してフラッシュに焼く。
   - 実行時は静的表の参照のみ（アロケータ不要・高速・確定的）。
   - **「YAMLは厳しい?」への回答 → ビルド時に使うぶんには厳しくない。** 厳しいのは *MCU上で実行時にYAMLをパースする* 場合（no_std/alloc・パーサのコード量・遅延）。本方式はホスト側で処理するため回避できる。
   - 代替: Rust native の **RON** も可（serde親和・スキーマ柔軟）。薙刀式の上流追従（IR-3）を最重視するなら、薙刀式 `.txt`（やまぶき形式）を直接読むコンバータを `build.rs` に実装する案も有力。
   - **推奨**: まずは **YAML中間表 + build.rs + phf**。将来 `.txt` 直読コンバータへ拡張。
4. **マトリクス配線【確定】**: §2.1 ピンアサイン表のとおり（14col×6row、行ストローブ推奨、極性はブリングアップで実測）。
5. **ローマ字綴り規則【確定（基準表）】**: 付録Bの基準表を採用。打鍵数最小のため訓令式ベース（`si/ti/tu/hu/zi…`）、撥音は常に `nn`。IME差異吸収のため綴り表は設定で差し替え可能とする。

## 付録B: ローマ字綴り基準表（FR-4.1 / §8.2-5）

方針: **打鍵数最小（訓令式ベース）＋ IMEが確実に受理する綴り**。撥音は常に `nn`。全綴りは設定で差し替え可能とする（MS-IME / Google日本語入力で受理確認すること）。

| かな                       | 綴り                                        | 備考                                                     |
| -------------------------- | ------------------------------------------- | -------------------------------------------------------- |
| し / ち / つ               | `si` / `ti` / `tu`                          | 訓令式（hepburn `shi/chi/tsu` も可、打鍵数で訓令式採用） |
| ふ                         | `hu`                                        |                                                          |
| じ / ぢ / づ               | `zi` / `di` / `du`                          |                                                          |
| ん                         | **`nn`**                                    | 母音・な行・`y` の前での誤連結を防ぐため常に2打          |
| っ（促音）                 | 次子音を重ねる（`kk/tt/ss…`）。単独は `xtu` | な行直前など重ね不可ケースは `xtu`                       |
| ー（長音）                 | `-`（ハイフンキー）                         |                                                          |
| ぁぃぅぇぉ（小書き）       | `xa/xi/xu/xe/xo`                            | `la…` でも可                                             |
| ゃゅょ（拗音）             | 結合して1語（きゃ=`kya`、しゃ=`sya`）       |                                                          |
| を / ゐ / ゑ               | `wo` / `wi` / `we`                          |                                                          |
| ヴ                         | `vu`                                        |                                                          |
| 外来音 ファ/フィ/フェ/フォ | `fa/fi/fe/fo`                               |                                                          |
| 外来音 ティ/トゥ           | `thi` / `twu`                               | MS-IME/Google受理                                        |
| 外来音 ディ/ドゥ           | `dhi` / `dwu`                               |                                                          |
| 外来音 ウィ/ウェ/ウォ      | `wi/we/who`                                 | `who`→うぉ（IME差異あり、要確認）                        |
| 外来音 ヴァ/ヴィ/ヴェ/ヴォ | `va/vi/ve/vo`                               |                                                          |

> 上記で吸収しきれないIME差異（特にうぉ・くゎ等）は、出力直前にIME種別プロファイルで切替えられる構造とする。
