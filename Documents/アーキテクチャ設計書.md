## 2. システム全体アーキテクチャ

### 2.1 物理構成

```
┌─────────────────┐   TRRS(4極) / UART0    ┌─────────────────┐
│  左半身          │  GP0(TX)⇄GP1(RX)×クロス │  右半身          │
│  Pico W          │◀──────────────────────▶│  Pico W          │
│  35キー/14col×6row│      +5V / GND          │  35キー/14col×6row│
│  WS2812B / GP28  │                         │  WS2812B / GP28  │
└────────┬────────┘                         └────────┬────────┘
         │                                           │
         │   どちらか一方が USB/BLE でホストへ        │
         └──────────────┐         ┌──────────────────┘
                        ▼         ▼
                   ┌─────────────────┐
                   │   ホスト PC      │  USB-HID もしくは BLE-HID
                   │  標準ローマ字IME │  （専用ソフト不要）
                   └─────────────────┘
```

- **対称ハードウェア**: TX/RXをコネクタでクロス配線済み → 左右で**同一ファーム・同一配線**。
- **役割は固定でなく動的**: ホストに繋がった側がマスタ（§3）。

### 2.2 論理レイヤ

```
┌──────────────────────────────────────────────────────────┐
│ L4 トランスポート層   USB-HID / BLE-HID（ホスト出力）       │  firmware/usb_hid.rs
├──────────────────────────────────────────────────────────┤
│ L3 変換層            かな → ローマ字 → HID Usage           │  naginata-core/{romaji,hid}.rs
├──────────────────────────────────────────────────────────┤
│ L2 入力方式層        同時打鍵判定エンジン（薙刀式）         │  naginata-core/engine.rs
├──────────────────────────────────────────────────────────┤
│ L1 統合層            自半身＋相方のキーイベントを sc に統合  │  firmware/main.rs + keymap.rs
├──────────────────────────────────────────────────────────┤
│ L0 物理層            マトリクススキャン / 分割UART / 手番   │  firmware/{matrix,split,handedness}.rs
└──────────────────────────────────────────────────────────┘
```

**設計原則:** L2/L3（入力方式の核）を **ハード非依存の `naginata-core`** に隔離する。
理由: 検証容易（ホストで単体テスト）＋ C/C++ 移植時に核を保てる（要件§8.1）。

## 3. 役割モデル（マスタ/スレーブ・手番）

2軸の独立した属性で各半身の振る舞いが決まる。

| 軸       | 値                | 決定方法                              | 実装                     |
| -------- | ----------------- | ------------------------------------- | ------------------------ |
| **役割** | マスタ / スレーブ | **USB列挙の成否**（VBUS電圧ではない） | firmware/main.rs（TODO） |
| **手番** | 左 / 右           | **EE_HANDS**（フラッシュ保存値）      | firmware/handedness.rs   |

```
            起動
              │
      ┌───────┴───────┐
      ▼               ▼
 USB列挙成功?      手番=read_hand()
   ┌──┴──┐            │
  Yes    No           ▼
   │      │      自分の手番表で
 マスタ  スレーブ   自半身を sc 化
   │      │
   │      └─▶ UARTで自半身イベントを送信専従（split.rs）
   │
   └─▶ 自半身(自手番表)＋相方(反対手番表)を統合 → Engine → 出力
```

- **なぜVBUSで判定しないか**: TRRSの+5Vが両半身のVBUSへ回るため、スレーブ側VBUSも5Vになり判別不能（要件§3.1）。USBデータ線の列挙（SOF/Configured）だけがホスト接続を示す。
- **手番はマスタ側だけで充足**: マスタは「自分の手番表」を自半身に、「反対手番表」を相方受信分に適用する。スレーブは生の(row,col)を送るだけでよい（`Hand::opposite()`）。

## 4. ソフトウェア構成（クレート/依存）

```
        ┌───────────────────────────┐
        │  naginata-firmware (bin)   │  no_std, thumbv6m-none-eabi
        │  embassy-rp/usb/time …     │
        └─────────────┬─────────────┘
                      │ depends (path)
                      ▼
        ┌───────────────────────────┐
        │  naginata-core (lib)       │  no_std（test時のみstd）
        │  phf / heapless            │  ← ホストで単体テスト可
        └─────────────┬─────────────┘
                      │ build-time codegen
                      ▼
        layout/naginata.yaml  ──build.rs──▶  phf テーブル(.rs)
```

- **2クレート分離**（単一ワークスペースにしない）理由: コアはホスト(std-test)、ファームは `thumbv6m` no_std。ターゲット/feature統合の衝突を避け、`cargo test` をコア側で素直に回すため。
- 依存方向は **firmware → core → (build時) layout** の一方向。逆依存なし。

### 4.1 モジュール責務一覧

| モジュール         | レイヤ | 責務                                                                            | 状態    |
| ------------------ | ------ | ------------------------------------------------------------------------------- | ------- |
| `core/keymap.rs`   | L1     | 生成テーブルのアクセサ。(row,col,hand)→sc、layer/combo2/combo3/mode照合、`Hand` | ✅      |
| `core/engine.rs`   | L2     | 同時打鍵判定 v3（シフト体系＋2/3キーコンボ＋編集モード, 大岡式遅延確定）        | ✅      |
| `core/romaji.rs`   | L3     | かな→ローマ字（訓令式ベース・撥音nn・促音・拗音・長音）                         | ✅      |
| `core/hid.rs`      | L3     | ASCII/シンボル→USB HID（Ctrl/Shift対応）                                        | ✅      |
| `core/build.rs`    | –      | YAML→phfコード生成（実行時パース無し）                                          | ✅      |
| `fw/matrix.rs`     | L0     | 14col×6row **COL2ROW**スキャン＋デバウンス＋is_held(起動時)                     | ✅ 実機 |
| `fw/split.rs`      | L0     | 左右UART KeyEvent/Statusフレーム・再同期                                        | ✅ 実機 |
| `fw/handedness.rs` | L0     | EE_HANDS フラッシュR/W（"NGHD"+L/R）                                            | ✅ 実機 |
| `fw/usb_hid.rs`    | L4     | HID キーボードレポート組立                                                      | ✅ 実機 |
| `fw/main.rs`       | L1     | 役割判定(USB列挙)＋EE_HANDS＋6タスク配線＋LED                                   | ✅ 実機 |

> 設計と実装の差分（実装で確定/変更した点）:
> エンジンは v3（pending＋held_shifts の順序非依存分解、2/3キーコンボの遅延確定、編集モード）。
> 役割判定は UART宣言ではなく USB列挙。UARTボーレートは 115200。最新の進捗は [issues/](issues/README.md) 参照。

## 5. データフロー（入力パイプライン）

```
 物理キー押下
   (row,col)
      │  matrix.rs: scan + debounce
      ▼
  KeyEvent(row,col,pressed)
      │  keymap::matrix_to_sc(hand)         ← 手番で表を選択
      ▼
   sc (u8: QWERTYスキャンコードID。薙刀式.txt と同じキー識別)
      │  engine.press/release(sc, now)      ← L2 同時打鍵判定（窓40ms）
      ▼
   かな ("か" / "きゃ" / "ふぁ" …)            ← single or combo
      │  romaji::kana_to_romaji()           ← "kya" 等
      ▼
   ローマ字 (ASCII)
      │  hid::romaji_to_hid()               ← 1文字ずつ
      ▼
   KeyPress{usage,shift}
      │  usb_hid::report_for() → release_report()
      ▼
   8バイト HIDレポート  ──チャネル──▶ USBタスク → ホスト
```

**キー識別子(sc)の設計判断**: 物理位置でも論理かなでもなく **「QWERTYスキャンコード相当のID」** を中間表現にした。
理由: 薙刀式の元定義（`.txt`）が `{か}|+24`、同時押し `+1e+1f` のように**スキャンコードでキーを表現**しているため、配列データを素直に転記でき、上流追従（要件IR-3）が容易になる。

## 6. 同時打鍵判定エンジンの状態機械（L2 詳細）

`engine.rs` の中核。**窓(window)＋候補集合(candidate)** モデル。

### 6.1 状態

| 変数          | 意味                                                       |
| ------------- | ---------------------------------------------------------- |
| `held`        | 現在押されている sc 集合                                   |
| `candidate`   | 現和音に含まれた sc の**最大集合**（窓内に押された全キー） |
| `chord_start` | 和音の開始時刻(ms)                                         |
| `emitted`     | 現和音を解決済みか                                         |

### 6.2 遷移

```
          press(sc)
   held空? ──Yes──▶ start_chord(now): candidate=∅, emitted=false
     │No
     ├─ 未解決 かつ (now-chord_start)>窓 ?
     │     └─Yes─▶ resolve()（前和音確定）→ start_chord(now)
     ▼
   held∪={sc}, candidate∪={sc}

          release(sc)
     held∖={sc}
     未解決? ──Yes──▶ resolve()
     held空? ──Yes──▶ reset()

          tick(now)   ※押しっぱなし対策
     未解決 かつ candidate≠∅ かつ (now-chord_start)>窓 ─▶ resolve()
```

### 6.3 resolve（候補集合 → かな）

```
candidate.len==1 ─▶ single_kana(sc)                    … 単打
        else      ─▶ pack(candidate) を COMBO 照合
                      ├ ヒット ─▶ combo_kana               … 同時押し（濁音/拗音/外来音）
                      └ なし   ─▶ 各scを昇順に single 出力  … PoCフォールバック
```

- **逆順許容**（FR-3.7）は `pack()` が集合をソートして u64 化することで自然に成立。
- **窓の起点**は「最初の押下」。逐次打鍵（窓超過）は前和音を確定してから新和音を開始するため、通常タイピングが同時押しへ誤判定されない。

### 6.4 未実装の拡張点（resolveの多段化で載せる）
- **センターシフト**（FR-3.3）: candidate に空白キーが含まれる場合、shift面テーブルを引く。
- **連続シフト**（FR-3.4）: シフトキーの押下保持を別状態で持ち越す。
- **後置シフト**（FR-3.5）: 先行確定キー＋後続シフトの**順序依存**履歴を見る（pack前に順序を保持する経路を追加）。
- **編集モード/ショートカット**（FR-4.2）: かな以外の「アクション列」出力型を resolve の戻り値に追加。

> 現状の戻りは「かな文字列」のみ。拡張時は `enum Output { Kana(&str), Action(KeyStroke列) }` へ広げる。

```

                                  │ SINGLE: phf::Map<u8,&str> │
```

## 8. 並行性モデル（embassy）

```
  embassy executor (cortex-m, single core で開始)
   ├─ scan_task         : 1ms周期。matrix.scan → engine → emit_kana
   │                       emit_kana が HIDレポートをチャネルへ try_send
   ├─ usb_task (TODO)   : embassy-usb。REPORTS を購読し HidWriter.write
   └─ split_task (TODO) : スレーブ時=送信専従 / マスタ時=受信して統合

  REPORTS: Channel<ThreadModeRawMutex, [u8;8], 16>   ← タスク間の唯一の共有
```

- **疎結合**: scan↔usb はチャネル1本のみ。ロック競合最小。
- **要改善（PoC既知課題）**: `emit_kana` は同期関数で `try_send`。満杯時にレポート落ちの恐れ。
  本実装では emit を async 経路（`send().await`）に移すか、リングを深める。

## 9. 主要シーケンス

### 9.1 単打「か」
```
matrix: (r,c)=press ─▶ keymap: sc=0x24 ─▶ engine.press(0x24)
key離す ─▶ engine.release(0x24) ─▶ resolve[単一] ─▶ "か"
"か" ─▶ romaji "ka" ─▶ hid {k},{a} ─▶ [press k][release][press a][release] ─▶ USB
```

### 9.2 同時押し「が」（2キー窓内）
```
press 0x1e (t=0, 窓開) ─▶ press 0x1f (t=5, candidate={1e,1f})
release 0x1e (t=30) ─▶ resolve ─▶ pack→COMBO hit ─▶ "が" ─▶ "ga" ─▶ USB
release 0x1f ─▶ held空 ─▶ reset
```

### 9.3 マスタが相方分を統合（TODO配線）

```
split.rx: KeyEvent(row,col,pressed)   ← スレーブから2byte
 ─▶ keymap::matrix_to_sc(hand.opposite(), row,col)
```

## 10. メモリ/フラッシュ・レイアウト

```
RP2040 2MB Flash
┌──────────┬─────────────────────────────┬──────────────┐
│ BOOT2    │ プログラム(.text/.rodata)    │ (末尾4KB)     │
│ 0x100    │ 配列テーブルもここ(rodata)    │ EE_HANDS等    │
└──────────┴─────────────────────────────┴──────────────┘
RAM 256KB : スタック / engine状態 / チャネルバッファ
```

- 配列テーブルは `rodata`（フラッシュXIP）に置かれRAMを消費しない。
- **EE_HANDS**: 末尾4KBセクタ先頭1バイトに `'L'/'R'`。`memory.x` で FLASH 長を削って専用領域化する案あり（handedness.rs / memory.x にメモ）。

## 12. 設計上のトレードオフ（記録）

1. **中間表現に sc を採用** … 上流(.txt)追従◎ / 物理配線とは別表が必要（matrix表）。
2. **YAML＋ビルド時codegen** … 実行時軽量◎・可読◎ / ビルド依存(serde_yaml)が増える。
3. **コアをno_std分離** … テスト容易◎・移植容易◎ / firmwareとの境界設計が要る。
4. **窓＋候補集合の簡易モデル** … 実装単純◎ / 後置シフト等は別経路追加が必要（§6.4）。
5. **2クレート非ワークスペース** … target衝突回避◎ / 依存パス管理が手動。

## 13. C/C++ 移植指針（§8.1 フォールバック時）

BLEがRustで詰まり pico-sdk(C/C++)へ移る場合でも、**L2/L3の設計はそのまま移植**できる:
- `engine`（窓＋候補集合の状態機械）→ C構造体＋関数群へ機械的に対応。
- `SINGLE/COMBO/MATRIX` → build時codegenを「C配列＋gperf(パーフェクトハッシュ)」に置換。
- `romaji`/`hid` → 純粋関数なので移植容易。
- L0/L4のみ pico-sdk + TinyUSB + BTstack で再実装。

→ 「核は言語非依存」を満たすため、移植コストは L0/L4 に限定される。
